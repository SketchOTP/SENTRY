# V0.2 Routine Statistics Foundation

This slice derives transparent, rebuildable routine summaries from trusted
SENTRY session and event history. It does not rewrite physical observations,
call Luna, or make routine data available to M4/M5 yet.

## Current implementation

- `perception/routines.py` implements four fixed routine types: observed office
  session start time, completed observed session duration, interruption-free
  absence between sessions, and first confirmed `primary_user` time per session.
- Ground-truth timestamps remain UTC. Analysis uses the configured IANA
  timezone (`America/New_York` in the Ubuntu production configuration) and
  uses circular statistics for clock times.
- Positive durations and intervals expose median, MAD, p25, p75, minimum,
  maximum, and relative MAD. Maturity is `insufficient`, `observed`, or
  `stable`; sample count and distinct local dates are both required.
- Restart-reconciled, uncertain, incomplete, and observability-interrupted
  evidence is excluded and its reason counts are retained in each snapshot.

## Storage and API

Schema version 5 adds append-only `routine_snapshots`. Snapshots contain the
algorithm version, source window, source-as-of, source fingerprint, timezone,
sample/date counts, maturity, derived statistics, and exclusion counts. They
are rebuildable derived data; physical sessions and events remain authoritative.

`tools/sentry_routines.py refresh` updates the local SQLite database and mirrors
it through the existing local-SQLite-to-Atlas snapshot path. An unchanged
source fingerprint is a no-op. `show` is read-only. The localhost-only API
endpoint is `GET /v1/routines`, returning the latest snapshot per routine key
by default; `?history=1` exposes bounded snapshot history.

## Resident refresh

`sentry-routines.service` is a separate systemd user oneshot and
`sentry-routines.timer` runs it two minutes after the authenticated user
manager starts and approximately every six hours. Routine refresh failure does
not stop perception, the state API, or proactive processing. `Linger=no`
remains the startup boundary; boot-before-login is not claimed.

## Qualification result

The actual production history was refreshed without seeding. It produced 40
latest snapshots (four routine types × ten scopes), all correctly marked
`insufficient`: the live database contains only a few observed sessions and
identity confirmations across too few distinct local dates. This is an
accepted sparse-data result, not a failed routine claim. Deterministic fixture
coverage and Atlas restore coverage are in `tests/test_routines.py`.

Routine statistics are not yet used in conversation or proactive judgment;
that requires a later Architect directive.
