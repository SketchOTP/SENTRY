# V0.3.1 — Always-Available Voice Foundation

This opt-in service adds hands-free request initiation to the existing local
voice chain. It does not change SENTRY's grounding, physical truth, reminder,
weather, routine, or proactive-policy boundaries.

```text
PipeWire 16 kHz PCM (memory only)
  → Vosk restricted wake recognizer ("Sentry")
  → bounded in-memory command segment (Silero VAD)
  → Whisper tiny.en command STT
  → existing sentry_ask.py
  → local Kokoro → PipeWire playback
```

## Privacy and activation contract

`sentry-voice.service` is installed but disabled unless the local mode-0600
configuration explicitly sets `voice.always_on_enabled` to `true`. The listener
keeps PCM only in RAM. Vosk locally recognizes the single configured wake token
and all non-wake audio is discarded without Whisper, `sentry_ask.py`, or Luna.
Its raw audio and recognized text are neither persisted nor logged.

The configured wake token is `Sentry`. Per the explicit owner policy, a
conversational use of that token can activate the assistant. Vosk is the sole
wake authority; Whisper only transcribes the command after Vosk wakes. “Sentry,
is anyone in the office?” sends the post-token command through the existing
grounded path. “Sentry” by itself opens an eight-second one-shot command
window. That initial-command state is distinct from the bounded conversational
follow-up state described below.

Vosk receives the same continuous PipeWire PCM stream as the bounded RAM-only
ring queue. It uses `vosk-model-small-en-us-0.15` with the non-forcing grammar
`["sentry", "[unk]"]` and only accepts a final exact `sentry` result. On wake,
the command-bearing segment remains in RAM and Whisper deterministically drops
everything through the first `Sentry` token. If no usable inline command can be
recovered, the listener enters the existing eight-second follow-up state.

## Endpointing and self-trigger protection

Silero VAD runs locally on 512-sample (32 ms) 16 kHz chunks. SENTRY retains a
1,000 ms in-memory pre-speech lead-in so VAD onset cannot clip the wake phrase.
Defaults are a 250 ms minimum speech duration, one second endpoint silence, a
twelve-second maximum segment, and a 500 ms post-speech re-arm tail. The shared
`SpeechActivityGate` uses a per-user runtime `flock`; both Kokoro reactive
speech and existing Speech Dispatcher proactive/reminder speech acquire it.
The listener discards VAD/Whisper dispatch while the gate is held, preventing
SENTRY's own output from becoming a command without adding a broker or daemon.

## Operations

Install the normal resident units as usual. Set `voice.always_on_enabled` only
in the ignored local production config to opt in, then enable/start the unit:

```bash
systemctl --user enable --now sentry-voice.service
python tools/sentry_voice_status.py
systemctl --user stop sentry-voice.service
```

The status file lives under the user runtime directory and records metadata
only: state, VAD health, last wake time, last command outcome, and last error.
It contains no audio or transcript.

## Conversation boundary

Whisper command text from both the explicit push-to-talk path and this optional
listener enters the same bounded conversational orchestrator. Luna first
selects from a fixed typed capability catalog; the local host validates and
executes at most three localhost API calls (one mutation), and a second bounded
Luna turn synthesizes only the returned fact IDs. There is no sentence-template
domain router, arbitrary tool execution, durable transcript archive, or
general conversational memory.

## Bounded conversational follow-up

After a Vosk-initiated user request is answered and its Kokoro playback has
completed, the listener waits in `FOLLOWUP_LISTENING` for one ordinary
wake-free user turn. The window is local, RAM-only, and governed solely by the
host:

- `conversation_followup_window_seconds` defaults to 8 seconds;
- `conversation_followup_max_turns` defaults to 2 wake-free turns after the
  initial `Sentry` request;
- each successfully delivered follow-up can open the next window only below
  that hard cap; silence, a failed capture, shutdown, or the cap returns to
  normal `LISTENING`, where `Sentry` is required again;
- an optional leading `Sentry` inside focus is stripped and remains one
  follow-up request, never a duplicate wake;
- PTT remains explicit and does not open hands-free focus; proactive, weather,
  reminder, startup, and error speech never opens focus.

The focus session reuses the existing per-conversation `ConversationOrchestrator`
context (at most four previous user/assistant turns, ten-minute TTL, RAM only).
It creates no transcript file, database row, embedding, or durable memory.
During Kokoro speech and the post-speech tail, the shared speech-activity gate
suppresses both wake and follow-up dispatch; barge-in is not supported.
